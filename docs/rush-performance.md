# 크레 러시: 개체 수에 따른 프레임 지연 조사

## 재현과 원인

기준 코드는 main `16b4f6d`입니다. 같은 시드·턴·상점·6웨이브 배치에서 보유 개체 수만 6 / 60 / 300으로 바꾼 검증 가능한 세이브를 사용했습니다. 각 개체는 실제 60좌위 유전체·공개 지식·건강 유전체를 가지며, 일반 게임 생성·표현형·저장 검증을 통과합니다. 플레이어 세이브나 새 게임의 시작 개체를 바꾸지 않습니다.

카페에는 보유 개체 수와 관계없이 항상 같은 10마리가 등장합니다. `CafeRush`의 프레임 시계도 원래 로컬 상태였습니다. 반면 800ms 체크포인트와 터치마다 다음 작업이 메인 스레드에 모였습니다.

1. `useHardcore.run → synchronizeTime → actWithTime → act`에서 시간 동기화와 전체 데이터 검증을 반복했습니다. `validateGame`은 기존 검증 계약을 투영하기 위해 전체 게임을 복제합니다.
2. `persistHardcore → makeSave / readSave`가 새 상태와 기존 상태를 검증하고 전체 JSON 체크섬을 계산했습니다. 정상 체크포인트 1회당 전체 게임 `structuredClone`이 15회 발생했습니다. 유전체·혈통·과거 기록이 많아질수록 비용이 증가합니다.
3. 저장 완료 때 복제된 전체 게임을 React에 넘겨 개체 참조가 모두 바뀌었습니다. `busy` 전환도 Hub를 갱신했습니다. 네이티브 모달 아래 컬렉션은 조작할 수 없어도 계속 렌더되어, 동일한 픽셀 스프라이트를 다시 계산·합성·그렸습니다. CPU 샘플에서도 픽셀 색 채우기와 레이어 합성 루프가 확인됐습니다.
4. 이 동기 작업 동안 `requestAnimationFrame`과 입력 이벤트가 함께 대기했습니다. 다음 프레임은 지나간 실제 시간을 따라잡아야 하므로 확대 위치가 크게 뛰었습니다. RAF를 더 호출하거나 판정 시간을 느리게 만드는 것으로 해결할 문제가 아니었습니다.

## 변경

- 수동 v1.2 / 저장 v9의 `stepRush`만 전용 Web Worker로 보냅니다. 기존 `synchronizeTime`, `actWithTime`, `persistHardcore`를 그대로 사용합니다. 유전체 검증·체크섬·기존 세이브 읽기·리비전 충돌 검사·게임/급여 상한 기록의 **동일 IndexedDB 트랜잭션**을 유지합니다.
- Worker는 준비 시점의 전체 상태를 보관하고, 이후 체크포인트에서는 작은 입력과 `cafeRush / revision / notices` 패치만 주고받습니다. React의 개체·알·부모·상점 참조를 다시 복제하지 않습니다. 알바 진입 및 시작 전에 준비하므로 큰 초기 전송이 점프 도중 발생하지 않습니다.
- 기존 행동 잠금을 유지하고 저장 성공 응답 후에만 진행·판정을 반영합니다. 저장 실패는 진행을 확정하지 않으며, 다른 창의 변경은 기존 `SaveConflict`로 처리합니다. 시작·급여·턴·일반 게임 행동은 기존 경로를 사용합니다.
- 모달 뒤 화면은 마지막으로 커밋한 React 요소 트리를 재사용합니다. 마운트를 유지하므로 선택·필터·스크롤을 보존하며, 닫을 때 최신 게임 상태로 갱신합니다. 닫힌 화면의 스냅샷과 수령 후 Worker 상태도 해제합니다.
- 매 프레임에 쓰는 기존 RAF·표시 시간 기준 터치 판정·아트 캐시·웨이브·최대 3,000원은 변경하지 않았습니다. 저장 간격도 800ms 그대로입니다.
- Worker를 사용할 수 없거나 시작하지 못하는 브라우저는 쓰기 전에 기존 저장 경로로 돌아갑니다. 이 호환 경로에서는 대규모 세이브의 성능 개선이 제한됩니다. 쓰기를 요청한 뒤에는 같은 요청을 임의로 재실행하지 않습니다.
- 저장 형식/DB 버전을 바꾸지 않았습니다. 서비스 워커 캐시 버전만 갱신했고, 온라인에서 읽은 Worker 청크도 기존 정적 파일 캐시 정책을 사용합니다.

## 측정 방법과 결과

CPU 지연 4배 조건의 최종 비교입니다. P95는 프레임 간격의 95백분위이며 낮을수록 좋습니다.

| 보유 개체 | 수정 전 P95 | 수정 후 P95 | 50ms 초과 프레임 전 → 후 |
|---:|---:|---:|---:|
| 6 | 83.4ms | 16.8ms | 104 → 0 |
| 60 | 383.3ms | 16.8ms | 118 → 1 |
| 300 | 1433.3ms | 16.8ms | 45 → 0 |

지연 설정이 없는 같은 클라우드 머신에서도 비교했습니다.

| 보유 개체 | 수정 전 P95 | 수정 후 P95 | 50ms 초과 프레임 전 → 후 |
|---:|---:|---:|---:|
| 6 | 16.8ms | 16.7ms | 0 → 0 |
| 300 | 66.7ms | 16.8ms | 51 → 0 |

4배 조건에서 메인 스레드 Long Task 누적 시간은 6 / 60 / 300마리 각각 8.9초 / 20.4초 / 24.7초에서 모두 0으로 줄었습니다. 플레이 중 컬렉션 props 커밋·배경 Canvas 그리기·DOM 변경·메인 스레드 전체 게임 복제도 모두 0회입니다. 수정 전 배경 Canvas 그리기는 각각 462회 / 680회 / 193회였습니다.

Worker 자동 저장은 각각 36회 / 36회 / 35회 실행됐고, 마지막 IndexedDB에는 원래 개체 수·턴·잔액 및 25,000ms / 10개 판정이 유지됐습니다. 응답은 최대 640바이트였습니다. 기존 저장 간격·전체 검증·판정 규칙을 유지한 결과입니다.

[수정 전 최종 원본](rush-performance/before-final.json) · [수정 후 최종 원본](rush-performance/after-final.json) · [기본 CPU 수정 전](rush-performance/before-native.json) · [기본 CPU 수정 후](rush-performance/after-native.json) · [CPU 샘플과 원본 코드 조각](rush-performance/cpu-hotspots.json)

- Chromium headless, 390×844, 프로덕션 webpack 빌드, CDP CPU 지연 4배. 실제 스마트폰 측정이 아니라 모바일 화면과 렌더러 CPU 부하를 재현한 브라우저 실험입니다. Worker까지 같은 비율로 지연된다고 전제하지 않았으며, 실제 코어 간 경합·전체 CPU 속도·발열을 재현하지 않습니다. 그래서 기본 CPU 조건도 별도로 비교했습니다.
- 표는 조건별 최종 1판의 관측값입니다. 최초 탐색 측정도 별도로 보존했습니다. 한 번에 한 브라우저만 실행하고 빌드·단위 테스트·E2E와 겹치지 않았습니다. 녹화와 서비스 워커는 성능 측정에서 제외했습니다.
- 25초 전 웨이브를 입력 없이 진행하고 마지막 저장의 결과 화면이 표시될 때까지 애니메이션·정기 저장·놓침 처리를 비교했습니다. 별도 E2E에서는 실제 터치와 다중 포획을 확인했습니다.
- RAF 간격, 50ms 초과 프레임, Long Tasks, 전체 복제, 컬렉션 props 커밋, 배경 Canvas 그리기 및 DOM 변경을 측정했습니다. Worker의 저장 횟수와 최종 IndexedDB의 25,000ms / 10개 결과도 읽어 저장을 생략하지 않았는지 확인합니다.
- `before.json / after.json`은 최초 재현 기록입니다. `before-final.json / after-final.json`은 프로파일러 준비 시간을 제외하고 React·Worker 계측을 추가한 최종 비교입니다. 전체 CPU 샘플 파일은 `/tmp`에 남기며 큰 원본을 저장소에 넣지 않습니다.

## 검증

- 기존 전체 행동 경로와 Worker 패치를 합친 게임이 v1·v2 모두 동일한지 단위 테스트합니다. 개체·유전체·혈통·알·턴·잔액을 유지하고 저장 왕복 및 정확히 한 번 지급을 확인합니다.
- 저장 실패 후 원래 리비전으로 재시도, 작은 메시지, 비알바 행동 뒤 재초기화, Worker 차단 시 호환 경로, 충돌 오류 전달을 테스트합니다.
- 모바일/PC E2E: 300개 실제 유전체를 유지하며 10마리 터치, 3마리 동시 출현, 표시 프레임과 판정 시간 일치, 중간 닫기, 오프라인 새로고침·계속하기, 중복 급여 방지, 손상된 기존 저장 거부·재시도, 다른 창의 리비전 충돌을 검증합니다.
- 기존 유전·브리딩·상점·성장·혈통·저장·미니게임 회귀 테스트를 모두 실행합니다. 관련 새 테스트는 `tests/rush-checkpoint.test.ts`, `e2e/rush-performance.spec.ts`입니다.

모바일 360×800에서 300마리를 보유한 채 10마리 전원 PERFECT를 기록한 [실제 결과 화면](rush-performance/result-300-mobile.png)도 남겼습니다.

주요 변경 파일은 `src/storage/rush-checkpoint.ts`, `rush.worker.ts`, `rush-client.ts`(기존 저장 경로 격리), `src/hooks/use-hardcore.ts`(잠금·준비·패치 반영), `src/components/hardcore/hub.tsx`(배경 트리 유지), `cafe-rush.tsx`(저장 오류 표시)입니다.

## 재측정

```bash
npm ci
npm run build
npm run start -- --port 3502
# 별도 터미널. Playwright Chromium을 먼저 설치해야 합니다.
PERF_URL=http://127.0.0.1:3502 PERF_LABEL=local \
  PERF_COUNTS=6,60,300 PERF_CPU_RATE=4 node scripts/benchmark-rush.mjs
```

시스템 Chromium은 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`로 지정할 수 있습니다. 비교 대상 버전도 별도 작업 트리에서 프로덕션 빌드해 같은 스크립트와 URL만 바꿔 실행합니다. 결과는 `docs/rush-performance/<label>.json`입니다. 스크립트는 검증된 임시 백업을 복원한 **새 브라우저 컨텍스트**만 사용하고 실제 사용자의 저장에 접근하지 않습니다.

## 한계

저장 자체의 전체 검증·복제·디스크 쓰기는 여전히 기록 크기에 비례하며 Worker CPU와 메모리를 사용합니다. 첫 진입·시작·급여 수령·백업·로드 시간까지 상수 시간으로 만든 것은 아닙니다. 대규모 복잡한 근친 혈통, 수천 마리, 실제 저사양 Android/iOS의 장시간 발열·메모리 조건은 별도 측정이 필요합니다. 브라우저의 단발성 스케줄링 지연을 완전히 없앤다고 보장하지 않습니다.
