# 플레이 누적에 따른 턴·저장 비용 최적화

기준 main은 `e6d140a`입니다. 플레이어 저장을 초기화하거나 읽지 않고, 실제 유전체 6/60/300마리와 실제 교배·산란·수거·부화·수령을 1/8/24회 진행한 월 규칙 저장으로 비교했습니다.

## 원인과 변경

턴과 저장 경로에서 같은 상태를 여러 번 검증했습니다. 특히 검증용 역사 스키마 투영을 위해 전체 게임과 상점 부모의 DNA를 깊이 복제한 뒤, 방금 복제한 고급 유전 필드를 제거했습니다. 과거 알을 검사할 때에도 출생 날짜 필드만 비교하기 위해 전체 배아를 복제했습니다. 개체와 번식 이력이 늘수록 복제·GC·상속 재현·JSON 비교 비용이 증가했고, 일반 게임 행동은 메인 스레드에서 이 작업을 수행했습니다.

- `validation-projection.ts`는 구조 검증이 수정하는 컨테이너와 기록만 복사합니다. 원본의 유전체·건강·상속·생애·상점 검증은 그대로 실행합니다. 알 수거/새끼 대기용 가상 기록도 검증 투영에만 생성합니다. 잘못된 배열을 정상 객체로 바꾸어 받아들이지 않습니다.
- 출생 날짜 필드를 공통 `birthMetadata`로 계산합니다. 실제 알의 `atBirth`는 기존 깊은 복사를 유지하고, 검증의 읽기 전용 비교는 큰 배아 복사를 생략합니다.
- 시간 동기화와 저장 reader는 이미 검증한 객체를 그대로 반환할 때 중복 검사를 반복하지 않습니다. 동기화·이전으로 새로운 객체가 만들어지면 결과 전체를 검증합니다. 호출 간에 검증 통과 상태를 캐시하지 않으므로, 같은 객체를 나중에 변조해도 다음 호출이 거부합니다.
- 저장 형식·IndexedDB 트랜잭션·체크섬 형식·충돌 검사·자동 급여·경제·턴 잠금과 350ms 연속 터치 방지를 유지합니다. 유전·외형 엔진과 UI는 변경하지 않았습니다. 기록을 삭제하거나 한도를 낮추지 않았습니다.

## Node 측정

동일 클라우드 머신의 Node 24/Vite에서 각 동작을 3회 실행한 중앙값(ms)입니다. 디스크·React 렌더링을 포함하지 않는 계산 시간이며, 실제 휴대폰 측정이 아닙니다. 측정 중 빌드·테스트·다른 브라우저를 동시에 실행하지 않았습니다.

| 저장 상태 | 턴 계산 전 → 후 | 저장 읽기 전 → 후 |
|---|---:|---:|
| 6마리 | 60.02 → 31.39 | 31.61 → 8.94 |
| 60마리 | 120.23 → 45.62 | 68.75 → 19.87 |
| 300마리 | 385.91 → 133.47 | 302.95 → 56.11 |
| 교배 이력 8회 | 559.58 → 99.92 | 228.81 → 44.69 |
| 교배 이력 24회 | 809.76 → 411.36 | 532.81 → 149.34 |

300마리 턴 계산의 전체/부분 `structuredClone` 호출은 59 → 5회, 24회 교배 이력에서는 353 → 8회였습니다. 모든 복제 수는 내부 함수 호출을 포함하며 전체 게임만의 횟수와는 다릅니다. 교배 이력 1/8/24회의 생성된 저장 체크섬이 전후 모두 같았습니다.

`makeSave` 단독 비용은 일관되게 감소하지 않았습니다. 24회 이력에서는 140.24 → 144.58ms였고, 이 경로에는 전체 검증·상속 재현·정규 JSON·체크섬 비용이 계속 남아 있습니다. 적은 반복 수의 GC·스케줄링 편차가 있으므로 모든 동작이 같은 비율로 빨라진다고 해석하지 않습니다.

## 실제 브라우저 측정

390×844 모바일 Chromium 프로덕션 빌드에서 6/60/300마리의 백업을 각기 새로운 브라우저 컨텍스트에 복원하고 실제 턴 버튼을 3회 눌렀습니다. 서비스 워커를 제외하고 CPU 배율 1을 사용합니다. 버튼 입력부터 저장 성공과 턴 잠금 해제까지 측정하므로 기존 350ms 보호 시간과 Playwright 왕복 비용을 포함합니다. 매 조건에서 3턴·정확한 사료 차감·잔액·모든 ID/DNA/외형 시드를 검사하고 새로고침으로 지속 저장을 확인합니다.

| 보유 개체 | 턴 완료 중앙값 전 → 후 | 3턴 Long Task 누적 전 → 후 | 턴당 전체 게임 복제 전 → 후 |
|---|---:|---:|---:|
| 6마리 | 1374.0 → 835.5ms | 1093 → 822ms | 14 → 1회 |
| 60마리 | 1079.6 → 910.7ms | 1375 → 1022ms | 14 → 1회 |
| 300마리 | 1900.4 → 1256.1ms | 2761 → 1522ms | 14 → 1회 |

최악 프레임 간격은 300마리에서 783.3 → 600.0ms였습니다. 지연이 완전히 사라진 결과는 아니며, 전체 계산을 Worker로 옮긴 것도 아닙니다. 각 조건은 3회뿐이고, 신규 상점 렌더와 브라우저 스케줄링이 포함되므로 작은 개체 수의 결과가 단조롭게 증가하지 않습니다.

## 검증과 한계

추가 단위 테스트는 동결한 주/월 저장·수거 대기와 새끼 수령 대기의 원본 불변, 300마리 검증 시 전체 게임 복제 없음, 같은 객체의 사후 변조 거부를 검사합니다. 알·건강 유전체·일반 유전체·월 달력·성장 규칙·미지 필드·배열 변조는 체크섬을 다시 계산해도 거부해야 합니다. 기존 전체 단위·브라우저 회귀 검사를 함께 실행합니다. 로컬 기본 2-worker 전체 단위 실행은 519개 중 510개 통과·9개 시간 초과였으며, 값 불일치는 없었습니다. 기존 제한을 유지해 관련 파일을 한 worker로 재검사하고 PR 전체 CI 결과를 별도로 기록합니다.

이 변경은 실제 저사양 Android/iOS, 장시간 발열과 수천 마리의 메모리 증가를 해결했다고 보장하지 않습니다. 과거 기록 자체와 상속 재현·직렬화 비용은 남습니다. 실제 플레이어 저장이나 특정 기기의 프로파일이 확보되면 남은 UI·혈통·저장 병목을 따로 측정할 수 있습니다.

## 재측정

```bash
PERF_OUTPUT=/tmp/game-node.json node scripts/benchmark-game.mjs
npm run build
npm run start -- --port 3503
# 다른 터미널에서 실행. 비교 버전도 같은 프로덕션 빌드 조건을 사용합니다.
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium \
  PERF_LABEL=local PERF_URL=http://127.0.0.1:3503 node scripts/benchmark-game-browser.mjs
```

Node는 임시 JSON만, 브라우저는 `docs/game-performance/<label>-browser.json`만 출력합니다. 사용자 브라우저·활성 IndexedDB 슬롯에 접근하지 않습니다.
